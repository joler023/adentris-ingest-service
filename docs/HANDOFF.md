## Decisions (short form)

| Concern | Decision |
|---|---|
| Intake durability | API publishes to RabbitMQ (persistent, publisher confirms), answers 202 after the confirm. No DB write on the request path. |
| Identity | No provider ID, so `eventKey = sha256(canonical(patientId, type, ts, data))`; unique index in MongoDB. |
| Delivery | At-least-once, manual acks. Idempotency = unique `eventKey` + atomic claim. |
| Per-patient serialisation | `crc32(patientId) % PARTITIONS` -> durable queue with `x-single-active-consumer`, prefetch 1. |
| Crash recovery | Lease (`lockedUntil`) on PROCESSING; takeover increments `attempts`, which fences all later writes. |
| Retries | One TTL queue per backoff step, dead-lettering back to the partition queue; exhausted -> `FAILED` + `events.dead`. |
| Ordering | Serial per patient in arrival order; late events (older `ts` than a completed one) are processed and flagged `outOfOrder`. |
| API docs | OpenAPI generated by `@nestjs/swagger` from the controllers and Zod schemas (Standard JSON Schema), rendered by Scalar at `/docs`, raw at `/openapi.json`. |

## Map of the code

- `src/main.ts` / `src/worker.ts`: the two processes. `ApiModule` / `WorkerModule` compose them.
- `src/configure-api.ts`: pipes + docs shared by `main.ts` and the tests.
- `src/events/`: Mongoose schema, `eventKeyOf`, `EventsRepository` (the whole state machine: `claim`, `complete`, `scheduleRetry`, `markFailed`).
- `src/messaging/`: `topology.ts` (exchanges/queues, `partitionOf`), `BrokerService` (confirmed publishing, reconnect).
- `src/ingest/`: controller, service, OpenAPI response schemas (`ingest.docs.ts`), Scalar setup.
- `src/processing/`: `EventConsumer` (acks, shutdown drain), `EventProcessor` (claim -> call -> record -> outcome), `ExternalSystemClient` (simulated).
- `test/`: integration tests and harness (`support/`). `scripts/load.ts`: load generator.

## Things to know before changing something

- Both processes declare the **full topology** on every connect. That is what stops the API from publishing into a missing queue (an unroutable message is confirmed by the broker and dropped). Keep it that way.
- `PARTITIONS` must match in API and worker and must only change with drained queues.
- `LEASE_MS` > `EXTERNAL_TIMEOUT_MS` is validated at startup; keep the invariant if you touch the timeouts.
- Add a field or status -> update the Zod response schema in `ingest.docs.ts`, which feeds the OpenAPI document. Add an endpoint or status code -> add the `@Api*Response` decorators and extend the OpenAPI assertion in `events.controller.spec.ts`.
- Integration tests use a dedicated RabbitMQ vhost (`ingest-e2e`) and database, recreated by `test/support/global-setup.ts`; they do not touch the dev data.

## Known limitations (all explained in ARCHITECTURE.md)

Fingerprint identity can merge identical distinct events; no absolute ordering (flag only); accepted-but-unclaimed events are visible only in RabbitMQ; extra workers are standbys, not load balancers; head-of-line blocking within a partition; zombie-consumer overlap for one patient is narrowed (fencing per event) but not fully closed; the dead-letter copy can be missed if the worker dies between `FAILED` and the DLQ publish (MongoDB stays correct); no health endpoints or metrics.
